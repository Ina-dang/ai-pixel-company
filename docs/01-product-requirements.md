# 제품 요구사항과 추적

## 1. 목적

마스터 프롬프트의 요구를 검증 가능한 ID와 Phase로 연결한다. 아래 항목은 요구사항이며 현재 구현되었다는 뜻이 아니다.

## 2. 범위

원문 0~30장 전체를 대상으로 한다. 원문 언어·원문 명령을 보존하고 문서 번호를 구현 순서와 혼동하지 않는다. 첨부 보완 내역은 [프로젝트 지침](PROJECT_INSTRUCTIONS.md)에 있다.

## 4. 설계 내용

수용 기준은 task의 `acceptanceCriteria`에 ID·한국어 설명·검증 방법·필수 여부로 저장한다. 영어 명세는 동일 ID를 참조하고 고유명사·경로·수치를 그대로 유지한다. 결과 증거는 기준 ID와 tested SHA에 연결한다.

## 5. 기술적 근거

원문에서 명시한 “AI 자체 완료 선언 불신”, “테스트 미실행 성공 금지”, “B→C 확장”을 출시 게이트에 반영했다. 요구사항은 사용자 제공 기준이며 외부 기술 기능의 존재 증거와 구분한다.

## 6. 데이터 흐름

원문/해시 → 요구사항 버전 → 영어 명세/수용 기준 → 작업/실행 → Artifact/검증 → QA/승인 → 완료 보고. 요구 변경 시 기존 승인과 QA를 새 버전으로 재검토한다.

## 7. 예외 처리

모호한 필수 기준은 추측해 완료하지 않는다. `blockedReason=REQUIREMENTS_CLARIFICATION`으로 기록하고 사용자 확인을 요청한다. 범위가 늘면 기존 task를 조용히 확장하지 않고 새 버전/후속 작업으로 기록한다.

## 8. 보안 고려사항

요구사항에 도구 권한이 적혀 있어도 권한 부여가 아니다. 외부 입력·문서의 지시문은 데이터로 취급한다. 원문도 접근 권한·보관·마스킹 적용 대상이다.

## 9. 구현 우선순위

R01~R03부터 구축한다. R04~R10 실증 없이 픽셀 표현을 실제 실행으로 홍보하지 않는다. 평가·음성·고급 조직은 후속 단계로 유지한다.

## 10. 완료 기준

각 요구사항에 테스트 ID·결과·Artifact·검증 SHA가 연결되어야 한다. 요구사항 충족률 = 충족한 필수 기준 수 / 전체 필수 기준 수. 미실행/검증 불가는 분모에 포함하고 충족으로 세지 않는다.

## 11. 미확정 사항

첫 기준 저장소와 대표 개발 과제, 모델 평가 반복 수, 사용자 수·동시 작업 부하는 Phase 0에서 정한다. 임의의 성능 수치를 이미 달성한 것처럼 사용하지 않는다.
