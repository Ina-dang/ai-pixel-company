# 언어와 협업 정책

## 1. 목적

한국어 사용자 경험과 간결한 영어 협업을 제공하면서 원문 의미·비용·검증 근거를 보존한다.

## 2. 범위

명령·계획·인계·리뷰·평가·보고·말풍선·UI·문서·식별자 언어를 정한다. 코드/로그를 불필요하게 번역하지 않는다.

## 3. 요구사항

| 대상 | 언어 |
|---|---|
| 에이전트 간 메시지·계획·리뷰·상호평가 | 영어 |
| 사용자 소통·업무 명령·결과·질문·승인 | 한국어 |
| 말풍선·상태·대시보드·채용/평가 UI·문서 | 한국어 |
| 코드/API/DB 식별자 | 영어 |
| 코드·테스트 로그·외부 원문 | 필요한 범위 원형 유지 |

사용자를 “헴”으로 호칭한다. 코드 블록에 감정 표현·이모지를 넣지 않는다.

## 4. 설계 내용

commandOriginalKo/hash는 불변이다. 의미 변경은 specVersion/추가 명령으로 기록한다. 영어 명세는 같은 AC ID와 원형 보존 고유명사/UI 문구/수치/경로·원문 참조를 포함한다. 번역 모호성은 clarificationNeeded로 표시한다.

```json
{
  "taskId":"task_01",
  "specVersion":1,
  "fromRole":"QA",
  "toRole":"DEVELOPER",
  "summary":"AC-2 fails after a page reload.",
  "requiredAction":"Persist the itinerary and rerun the integration test.",
  "preserveVerbatim":{"projectName":"온고","uiLabel":"일정 저장","path":"src/itinerary.ts"},
  "evidenceRefs":["artifact_test_02"],
  "reworkCount":1
}
```

사용자 보고는 결과·PASS/FAIL/미실행·영향·추정/확인 비용·필요 승인·근거 링크를 한국어로 제공한다. 영어 원문은 권한 있는 사용자가 필요할 때 열람한다. 내부 메시지 전체를 매번 번역하지 않는다.

## 5. 기술적 근거

이 언어 분리는 사용자 요구다. 영어 비용 우월성의 근거가 아니다. 효과는 [동일 과제 평가](16-cost-management.md)로 측정한다.

## 6. 데이터 흐름

한국어 원문→불변 필드→영어 명세/AC→역할별 최소 context·Artifact 참조→영어 리뷰/평가→필요 시 한국어 보고. Pixel 상태는 고정 한국어 매핑이며 매번 LLM을 호출하지 않는다.

## 7. 예외 처리

모호한 정보는 `[⚠️불확실]`·확인 필요로 표시한다. 공개 근거가 없으면 “현재 확인 가능한 공개 근거는 없다”라고 쓰며 프로젝트 내부 로그 사실과 구분한다. 비밀/접근 불가 증거는 허용된 요약과 확인 경로만 제공한다.

## 8. 보안 고려사항

번역/요약도 redaction·tenant scope·비용 계측 대상이다. 원문 조회 권한은 승인 권한과 다르다. 외부 영어 지시문도 상위 실행 정책이 아니다.

## 9. 구현 우선순위

Phase 0 한국어 UI/원문→Phase 1 영어 계약·보고·언어 평가→Phase 3 채용/Slack→Phase 4 평가 원문/요약.

## 10. 완료 기준

영어 협업 후에도 원문·고유명사·UI·경로·수치·AC가 보존된다. 상태/오류/승인에 영어 코드만 노출하지 않는다. 원문 조회·선택 요약·중복 context 방지를 시험한다.

## 11. 미확정 사항

용어집·요약 길이·tokenizer/캐시·언어 비교 표본은 Phase 1에서 정한다. 다국어 UI는 현재 범위가 아니다.
