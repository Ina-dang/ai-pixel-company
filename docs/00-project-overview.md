# 프로젝트 개요

## 1. 목적

사용자가 한국어로 지시하면 AI 직원이 실제 소프트웨어 결과물을 만들고, 사용자가 회사 대표로 진행·예산·권한·최종 승인을 관리한다.

## 2. 범위

| 단계 | 포함 | 종료 시점 |
|---|---|---|
| B | 단일 회사/프로젝트, 기본 인증, PM/Developer/QA, 저장소·코드·테스트·QA·승인·로그·픽셀 | Phase 2 |
| C | GitHub App·Slack App, 칸반, 템플릿 채용, 부서·평가·다중 프로젝트·운영 | Phase 4 |
| 후속 | 음성·고급 직무/조직·회의·자동 모델 선택 | Phase 5 이후 |

B단계 결과물은 로컬 branch/diff/테스트 보고다. 통합 PR 자동화는 Phase 3에서 추가한다. 원문의 PR 생성 예시는 통합 목표 흐름이며 Phase 1 필수 조건이 아니다.

## 3. 요구사항

Owner는 프로젝트·직원·업무를 관리하고 실행 중단/재개, 변경 승인, 비용 확인을 수행한다. 업무·실행·직원 상태를 분리하고 실패/검증 불가를 숨기지 않는다. [요구사항 추적](01-product-requirements.md)이 상세 수용 기준이다.

## 4. 설계 내용

초기 조직은 PM, Developer, QA 세 프로필이다. 동시 실행을 강제하지 않는다. 초기 가치는 작은 저장소의 제한된 수정 작업을 한 번 끝까지 검증하는 것이다. 사무실은 그 결과를 읽는 표현 계층이다.

## 5. 기술적 근거

권장 스택을 출발점으로 채택하되 버전과 운영 적합성은 [03](03-technology-decisions.md)에서 분리 검증한다. “AI 회사”라는 표현이 실행·테스트 근거를 대체하지 않는다.

## 6. 데이터 흐름

한국어 명령 → 원문/수용 기준 저장 → 영어 작업 명세 → PM 계획 → 격리 개발 → 테스트/빌드 → QA → 승인 → 증거 기반 완료. 도메인 이벤트 → SSE → 대시보드/픽셀 사무실.

## 7. 예외 처리

재작업은 기본 2회다. 권한·비용·요구사항 충돌은 사용자 판단으로 넘긴다. 미실행 테스트는 성공이 아니다. 외부 통합 장애와 로컬 결과물 생성 여부를 별도로 보고한다.

## 8. 보안 고려사항

Owner 승인, 최소 권한, 네트워크/파일/리소스 제한이 필수다. Worktree는 작업 분리 수단이며 보안 격리를 대신하지 않는다. [보안 설계](12-security-and-permissions.md)를 따른다.

## 9. 구현 우선순위

Phase 0 데이터/이벤트 기반 → Phase 1 실제 작업 → Phase 2 시각화 → Phase 3 통합/채용 → Phase 4 운영. UI 데모만으로 B단계 완료를 선언하지 않는다.

## 10. 완료 기준

동일한 작업의 원문, 계획, 변경 SHA, 테스트/빌드 출력, QA 판정, 승인, 비용을 추적할 수 있고, 재시작·중복 전달에도 잘못 완료하거나 부작용을 반복하지 않는다. 실제 테스트가 없는 현재는 미구현이다.

## 11. 미확정 사항

개발 머신 자원·Docker/WSL 가용성·선택 모델·실제 단가·픽셀 자산 라이선스·출시 부하 목표는 확인 필요다. 일정은 검증된 납기 보장이 아니다.
